# 手机端自动化 Agent v1 架构

状态：骨架 v0.1（2026-10-24）。以第 0–3 关的实测为依据；标“建议”的是 Agent 的提议，等你确认。标“M1”“M3”“M4”的是计划在对应里程碑做、现在代码里还没有的部分；标“待真机定”的等 QQ 真机结果再决定。

## 1. v1 做什么、不做什么

**做：** 侧载安装的免费安卓 App，用户说一句话（或点一下），App 在前台执行官方任务包。首批三个任务：

1. 打开微信最上面的会话，复制最新一条消息，然后打开小红书
2. 打开 QQ 最上面的会话，复制最新一条消息，然后打开抖音
3. 打开夸克浏览器，打开首页上名为“书签”的网站（2026-10-25 改：见第 9 节 M2 状态）

**v1 包含学习模式的最小部分“补教”：** 某步失败时用户点一下正确位置；补教后**整个任务成功完成**，就把补教结果保存成本机任务包变体（叠加在官方包上，记录目标 App 版本），下次直接用。

**不做（v1，以后可能做）：** 完整学习模式（演示录制、泛化）与任何生成式模型；虚拟屏 / 后台运行；通知监听；应用分身；任务参数（这三个任务没有参数）；文字输入动作（不变量已放开，见决定记录，要做先过安全评审）；发送类动作；在 App 里嵌 WebView。

**落地标准（沿用第 0 关定义）：** 在 Neo5 和另一台手机上，三个任务各连续跑 20 次，成功率 ≥ 95%；一个朋友能按说明自己侧载、开启无障碍并跑通。

## 2. 实测依据（第 0–3 关）

| 项 | 结论 | 对架构的影响 |
|---|---|---|
| 界面树 | QQ、夸克可用（会话行有 content-desc，“复制”、书签行有文字）；**微信在真实无障碍服务下也几乎为空**（微信自己的节点 1–8 个，0 个带文字） | QQ、夸克走界面树；微信走截图 + OCR |
| 截图 | 各 App 均未禁止截图 | 无障碍 `takeScreenshot`（API 30）可用 |
| 速度 | 界面树每步约 0.7–2.8 s，主要是 App 自己的响应；手机上 OCR 每步约 1 s 以内 | 不追求更快的感知，等待策略比感知速度更重要 |
| 启动 | 按包名 Intent 启动小红书、抖音成功；**应用分身启动失败** | 用 Intent 启动；v1 不支持分身 |
| 复制确认 | 微信复制有 toast“已复制”；QQ 没有 | 微信用 toast 确认；QQ 用“菜单关闭且无错误”弱确认 |
| 保活 | 打开“后台高耗电”后服务稳定 | 写进安装引导 |
| 开发能力 | 构建、安装、调试已走通（`D:\gui-agent\spikes\a11y_probe`，不在本仓库） | 用 Kotlin，探针代码可直接迁移 |
| 系统版本 | Neo5 当前 Android 13 | minSdk 30，13 起侧载应用要“允许受限设置” |

## 3. 结构

两个 Gradle 模块，加任务包和小工具。不另起框架。

`core` 按子包组织，包名 `dev.phoneagent.core.<子包>`（2026-10-25 拆分，见决定记录）。`core/CLAUDE.md`、`app/CLAUDE.md` 是各模块的开发说明：

```
core/    纯 Kotlin（JVM 单测，秒级）
  pack/        任务包数据类 + JSON 解析与校验（kotlinx.serialization）：Pack.kt、Validator.kt
  run/         解释器：逐步执行、找目标、等稳定、检查预期、失败停下：Runner.kt、Device.kt、Frame.kt
  route/       一句话 → 任务（别名匹配）：Router.kt
  ext/         扩展点注册表和 v1 内置实现：Registry.kt、Builtins.kt

app/     Android
  AgentService （AccessibilityService，由探针的 ProbeService 演进而来，实现 core 的 Device 接口）
  MainActivity 任务列表（v0.1：每个任务包一个按钮，跑完显示原因和每步耗时）
  Ocr.kt       onnxruntime-android + PP-OCR det/rec（从 OcrBench.kt 迁移）——M3
  ui/          运行清单（每步状态 + 补教/跳过/停止）、安装引导——M4

packs/   官方任务包 JSON（v1 三个；现在只有 QQ 的草稿）
tools/   probe/probe.py（抓树/截图/对比）
```

`Device` 接口：`capture`（取一帧）、`launch`、`press`（点 / 长按）、`back`、`awaitSettle`（等稳定）、`nowMs`。它不只是“屏幕”，还管启动、返回和等待，所以不叫 `Screen`（见决定记录）。

任务包校验不另写脚本：`core` 的测试 `shipped packs validate` 校验 `packs/` 里的每个文件，`.githooks/pre-push` 在推送前跑 `:core:test`。

`core` 不依赖 Android，这样解释器、匹配、任务包校验都能用录下来的界面树在电脑上测。

### 扩展点

依据 `docs/research/bettergi-speed-and-plugins.md` 与 `docs/research/onedragon-speed-and-plugins.md`。两个项目的可插拔都是“**代码封闭、数据开放**”：社区贡献的是数据（识别配置、YAML/JSON 策略），数据只能引用代码里已注册的名字。v1 照此办理：**任务包只能是数据；扩展点是按名字注册的实现（`core/ext/` 里的 `Builtins.registry`），编译期注册，未知名字在加载任务包时由 `validate` 拒收**。不做运行时代码插件、脚本引擎，不动态加载 dex。

| 扩展点 | 形态 | v1 内置 | 状态 |
|---|---|---|---|
| `Perception` | `capture(): Frame`。`Frame` 带 `id`、前台包名、可选界面树、可选截图，以及按需计算的 `ocr(region)`，同一帧同一区域只识别一次 | `TreePerception`、`ScreenshotOcrPerception`；OCR 背后再隔一层 `TextRecognizer`，方便以后换模型或加 NNAPI | 现在由 `Device.capture()` 直接取帧，`Frame` 还没有 `id` 和截图；`ocr(region)` 按区域缓存和 `TextRecognizer` 已有。M3 已有：`Perception` 接口（`Device` 继承它）、`Frame.id`、`Frame.screenshot`（第一次用到时才截图，只在内存里）；`AgentService` 一个类同时读树和截图，不拆成 `TreePerception` / `ScreenshotOcrPerception` 两个类。OCR 识别器待接 |
| `Finder` 注册表 | 名字 → 实现；每个 Finder 声明自己需要的能力（`ocrText` 需要 `ocr`），任务包 `needs` 里没写就拒收；截图在找法第一次用到时才截 | 已有：`text` `desc`（可 `exact`）`id` `listItem`（`in` 指定容器，不写就用最大的可滚动节点；负数从末尾数）`lastMessage`（聊天区最下面一条消息气泡，跳过整行宽的系统提示）`ocrText`（可带 `region`）`lastBubble`（界面树为空时按截图版面找最下面一条消息）`chatRow`（截图里的会话列表，跳过 `skip` 里的名字） | 锚点叫 `in` 还是 `under` 待定；其他找法是否也支持 `region` 待定；预留 `template` |
| `Expectation` 注册表 | 同上 | `anyText` `gone` `toast` | 已有；`screen` 在加 `ScreenDef` 时一起加 |
| `Action` 注册表 | 名字 → 实现，和 Finder 一样可扩展（以后加滚动、左滑右滑等）；但只能由 App 代码新增并经安全评审，任务包只能引用已注册的动作。仍然不含输入与发送。内部先试 `performAction`，不行再退回手势 | `launch` `tap` `long` `back` | 已有 |
| `ScreenDef`（可选） | `id`、`app`、`marks`（若干 Finder，全部命中才算这个画面），只在前台包名匹配的画面里判定；预留 `goto` 字段，不做路由 | — | M3 前 |
| `PackSource` | 内置包（assets）、签名下载包、本地补教补丁（只能改坐标）。官方包 id 唯一，冲突时先注册者胜并告警 | 内置 + 补丁；签名下载在做更新渠道时加 | M4（和补教一起做）。现在 `MainActivity` 直接读 assets；内置包 id 不重复由 `shipped packs validate` 检查 |
| `Trace` | 每步记录 找 / 动 / 等 / 查 四段耗时和结果码，不含界面内容 | `StepTrace`（另含命中的找法序号、目标边界、尝试次数） | 已有 |

## 4. 任务包格式

一个任务 = 若干步，每步写“做什么、怎么找、做完该看到什么”。找法按顺序尝试，前一个找不到才用下一个。

真实的例子见 `packs/qq-latest-to-douyin.json`（不在这里抄一份，免得漂移）。它的步骤：启动 QQ（预期有“联系人”标签且没有侧边栏的“返回”；不满足就按返回键，最多 3 次）→ 点底部“消息”标签 → 点会话列表第一行 → 长按聊天区最下面一条消息 → 点“复制” → 启动抖音。

- **找法种类**（v1 只做需要的）：已有 `text`、`desc`（先精确匹配，再退到“包含”；加 `"exact": true` 不退，用于“消息”这类会被更长文字包含的短标签）、`id`、`listItem`（容器里第 N 项，负数从末尾数；`in` 指定容器）。`lastMessage`：聊天列表里从下往上第一个含“比列表窄的可长按节点”的条目，取其中最大的那个（气泡）；系统提示（撤回、入群、精华）是整行宽，被跳过（依据 2026-10-25 QQ 文字/图片/视频/语音/系统提示的界面树）。`lastBubble`：`lastMessage` 的截图版，给界面树为空的 App 用（微信）。在两侧固定的头像列里找最下面的头像，取紧挨着它的气泡；系统提示和时间居中、没有头像，所以会被跳过；语音消息后面的未读红点和“转文字”按钮按间隙切开，不算进气泡。尺寸都按屏幕宽度的比例算，不依赖分辨率（依据 2026-10-26 微信深色模式下文字、图片、语音、表情、系统提示、收发两侧共 6 张截图，全部命中，每张 4–40 ms）。`chatRow`：截图里会话列表的第一行，但名字（头像右边上半行，只跑识别）含 `skip` 里任一词的行跳过，用于跳过公众号、服务号、腾讯新闻等非聊天入口；置顶行背景更浅，按每行左边距的颜色判断背景。`skip` 写在任务包里，遇到新的非聊天入口就往里加。`ocrText`：截图 OCR 读出的文字（微信用），匹配规则同 `text`（忽略空白，可 `exact`），目标只有坐标、没有节点。坐标只作为补教结果存在本地，不写进官方包。
- **预期**：`anyText`（界面上出现某些文字之一）、`gone`（某文字消失）、`toast`（出现指定提示）。微信步骤的预期用 OCR 文字判断：`anyText` / `gone` 也可以写成 `{"text": [...], "region": [...]}` 或 `{"text": [...], "near": f}`，只 OCR 一部分（整屏 OCR 在后台约 4.5 s）。`near` 是围绕上一个动作目标的整宽横条，上下各伸出屏高的 f，比如长按消息后弹出的菜单；`ocrText` 也支持 `near`，在预期刚成立的同一帧上用同一横条，直接复用那次 OCR。
- **画面变没变**：返回到首屏、等用户关弹窗时要判断画面是否变了。界面树为空的 App（微信）树永远一样，所以有 OCR 的运行在树相同时再比截图（粗网格上超过 1% 的点明显变化就算变了）。截图被系统以“间隔太短”拒绝时重试，最多 1 s。
- **`ifMissing`**：找不到目标时给用户看的人话原因，而不是笼统的“失败”。
- **包头字段**：`schemaVersion`（必填，现在是 1）、`version`、`author`、`needs`（如 `["ocr"]`）、`testedWith`（如 `{"com.tencent.mm": "8.0.x"}`）。App 不认识的 `schemaVersion` 或缺少 `needs` 里的能力时，加载就拒收，不会跑到一半才失败。解析是严格的：不认识的字段直接报错。补教补丁记下当时的目标 App 版本，版本一变就提示“补丁可能失效”。
- **每步可选**：`timeoutMs`（默认 5000）、`maxRetry`（默认 1）。`ocrText` 可带 `region`：屏幕比例矩形 `[left, top, right, bottom]`，取值 0–1，和 `Box` 同序，只检测、识别这一块。区域位置已知、只有一行字时跳过检测、只跑识别（`Frame.ocrLine`），任务包里怎么写待定（M3）。
- `listItem` 的具体规则（容器怎么认、哪些行算条目、怎么跳过时间分隔条和系统提示）在实现 QQ 任务时按实际界面树定，微信版本按截图版面定。现在的实现只取容器的直接子节点里可点或可长按的那些，按上边缘排序。（建议，待真机定）

不做：画面路由图、多版本变体、参数槽。三个任务都从“启动 App”开始，启动后的首屏就是固定起点；遇到不在预期首屏的情况（例如停在某个聊天里），v1 先按返回键回到列表，最多 3 次，仍不对就停下。已实现（2026-10-25）：`launch` 步的 `expect` 不满足时，`Runner` 按返回键再查，最多 3 次；每次按之前确认前台仍是 `requires` 里的 App，否则停下（`NO_EFFECT`）。用已有的 `back`，动作集不变。

## 5. 运行时

每一步：

1. **找目标**：按 `find` 顺序找，代价从低到高：界面树 → 区域 OCR（位置已知时只识别）→ 整屏 OCR。整屏 OCR 时检测不缩小输入（桌面端实测，长边缩到 960 会让小字召回明显下降；OneDragon 用 960 没问题，是因为它送进去的几乎都是裁好的小区域）。找不到就等界面事件后重找，直到 `timeoutMs`（默认 5 s）。
2. **动作**：优先 `performAction`（CLICK / LONG_CLICK）；目标不可点时退回手势（按控件中心点）。
3. **等稳定**：动作后等到出现界面变化事件，并且 300 ms 内没有新事件（`Device.awaitSettle`，来自探针里的 `waitForSettle`），上限是该步的 `timeoutMs`。不写固定 sleep。
   现状：`AgentService.awaitSettle` 从调用时刻起算 300 ms 静默，**动作没有触发任何事件时也会在 300 ms 后返回**，靠后面的“查预期”兜底。是否改成“必须先出现事件再算静默”，待真机定（看每步“等”的耗时和失败原因）。
4. **查预期**：读树（或截图 OCR）检查 `expect`。每一轮的结果分四种：成功；**等待**（界面还在变、还在加载，不计重试次数，只受时间上限约束）；**重试**（点了没反应，计次数，最多 `maxRetry` 次）；失败。重做动作前先重新感知一次，确认确实还停在原处才重做，避免长按菜单这类操作被触发两次。代码里失败分为 `Outcome.MISSING`（找不到目标）、`WRONG_APP`（前台不是 `requires` 里的 App）、`NO_EFFECT`（动作后没出现预期）、`ACTION_FAILED`（动作没执行成功）。
5. **停下时**：运行清单标出这一步和原因，给三个选项：**教我这一步**（用户点一下正确位置，存为本地补丁，只对这台手机、这个 App 版本生效）、**跳过**、**停止**（M4）。v0.1 只在跑完后由 `MainActivity` 显示停止原因和每步耗时。

**交互的两层：**

- **core 里的 `RunObserver` 接口**：`onStep(trace)` 报告进度；`onStuck(step, reason)` 在卡住时返回用户的选择（教我＋坐标 / 跳过 / 停止）。补教、跳过、“补教后整个任务成功就保存为本机变体”都在这一层，用脚本化的测试覆盖。界面只负责把它画出来。`onStep` 已实现（`MainActivity` 每完成一步就刷新耗时）；`onStuck` 和补教在 M4。
- **悬浮面板**（M4）：任务运行时目标 App 在前台，我们的 Activity 被挡住，所以运行清单和三个按钮放在悬浮于目标 App 之上的小面板里。面板由无障碍服务创建叠加窗口（`TYPE_ACCESSIBILITY_OVERLAY`），不需要另外申请悬浮窗权限。“教我这一步”就是在面板上让用户点一下屏幕位置。面板同时标出 Agent 将要点的位置，用户随时能看见、随时能停。

微信步骤的感知：截图 → 按版面规则裁出区域（列表第一行、聊天区最后一个气泡）→ OCR → 得到文字和位置。截图和 OCR 结果只放内存，步骤结束就丢弃。

OCR 会话：只在任务包 `needs` 含 `ocr` 时创建；启动目标 App 的同时，用实际输入尺寸把检测和识别各预热一次（OneDragon 只预热了检测）；识别在 GPU 上（LiteRT，编译好的 GPU 程序缓存在 `cacheDir/litert`，只有第一次启动要编译），检测和 GPU 不可用时的识别用 onnxruntime CPU（关闭线程池自旋和内存池、线程数 4）；模型暂定 PP-OCRv6 small（见决定记录）；整个进程只有一个实例，调用串行执行。

**OCR 效率（目标：用尽一切可用办法压低耗时；“改动最小”让步于这个目标）。** 按清单逐项做、逐项在 Neo5 上实测。实验数据、判分方法和重跑命令都在 [ocr-experiments.md](ocr-experiments.md)，这里只列做了什么、还剩什么：

- 方法：准确率相关的变量（检测框阈值、扩框比例、检测最长边、每批行数）在电脑上对标准答案做全组合，不逐个贪心地定；速度相关的变量（线程、推理后端、批量、最长边）在手机上做全组合。旋钮都在 `OcrConfig`，每次调用的分段耗时在 `PpOcr.timings`。判分（`OcrScore`）在手机上和电脑上逐个数字相同，所以准确率实验在电脑上做，手机只测速度。默认配置（检测最长边 2240）下短标签（≤4 字）读对 89.7%，微信 32/32；长文字读对率只有一半，主要是标准答案本身的问题（树里的文字比屏幕上显示的长、相邻文字连框、压暗的背景字），见实验记录第 2 节。
- 已做：模型选型实测（v6 tiny / small / tiny 检测 + small 识别，见决定记录）；检测、识别线程数分开实测（2/4/6/8 × 1/2/4，各自都是 4 最快，两段耗时互不影响）；关闭线程池自旋；按需截图（找法用到才截）；同一帧按区域缓存 OCR 结果；截图最小间隔实测（约 0.35–0.45 s）；只识别需要的区域（`Frame.ocr(region)`）；位置已知的单行只跑识别（`Frame.ocrLine`）；任务包需要 OCR 时在后台加载并按屏幕尺寸预热，和启动目标 App 重叠；识别按宽高比排序、6 行一批；检测输入缓冲复用（整屏约 30 MB，不每次分配）；只打包 arm64；标准答案（33 张截图 347 个标注）和准确率全组合，结论是整屏检测不缩小，阈值 0.45 和 0.6 没有差别。
- 预处理改为整行写入、分 4 份并行，解码并行，推理输出少一次复制：输出不变，手机整屏 4489 → 约 3200 ms，下 1/4 屏 1173 → 790 ms。
- 识别放到 GPU（LiteRT）：每批 6×320 从 199 → 68 ms，读法不变；检测留在 CPU（见决定记录）。
- 试过、没用的：
  - NNAPI：可变尺寸时整图退回 CPU；固定尺寸后驱动接不下整图，退回 CPU 时内存超 1 GB 被杀。
  - XNNPACK：跑检测慢 3 倍；跑识别在 onnxruntime 1.20.0 里段错误。
  - 两段都留在 CPU。按段选后端的开关（`detProvider` / `recProvider`）保留，升级 onnxruntime 后重测。
- 最近一次手机分段（改写后，整屏 40 框约 3200 ms）：识别推理约 1.9–2.3 s（六成），检测推理约 1 s，其余合计约 0.3 s。
- 下一步（按预计收益）：
  - 识别推理是最大的一块：int8 量化（电脑 x86 上更慢，手机 ARM 未测）、升级 onnxruntime 后重测 XNNPACK、把 ORT 线程绑到大核（`session.intra_op_thread_affinities`）。
  - 区域内缩小检测输入：整屏缩到 1280 能省约 0.6 s，但会掉准确率，区域内可能不会。
  - 预处理已降到约 0.1 s，暂不需要挪到原生（ONNX 图内归一化、Bitmap 缩放、OpenCV for Android 约 +10 MB）。
  - 解码已降到约 70 ms：还可以把 argmax 放进图里，输出从“步数 × 18710”降到“步数”；或者用固定输出缓冲（pinned output），省掉拷贝。
- 从调研补上的，还没做：确认 ORT 图优化全开和内存复用（OneDragon 注释称 CPU 快 10–30%，Java 版可能已默认）；对照参考改用 PaddleOCR 官方推理流程（不再依赖 gui-agent 的 Python 引擎）。
- 之后逐项试：
  - 区域内检测输入缩小：整屏缩小会掉准确率，区域可能不会。
  - 树层把有边界没文字的容器交给 OCR（第 11 节）。
  - 检测和识别流水线并行。
  - 固定图标用模板匹配代替 OCR。
  - 后置谓词一满足就进下一步（第 11 节）。
  - 模型资源不压缩、按内存映射加载，省去把 31 MB 读进堆。
  - 检测概率图只在需要的区域上做连通区域。

**不照搬：** 两个项目的界面流程都大量使用固定 sleep（BetterGI 有 754 处写死的毫秒数；OneDragon 有 393 处 `wait=1`），并且是“先睡一会儿再查”的轮询。手机上有界面事件可用，保留“事件加 300 ms 静默”的等待方式。

## 6. 不变量（安全与隐私）

- **只在用户主动检查更新时联网**（固定地址、任务包签名校验，见第 10 节）；执行任务的过程中永不联网。
- **只操作任务包 `requires` 里列出的 App**；当前前台不是它们时不点任何东西。
- **v1 动作集只有：启动 App、点、长按、返回。** 没有发送。文字输入不再是不变量（2026-10-26 用户决定），但还没有这个动作，加之前要过安全评审。
- **界面内容不落盘。** 树、截图、OCR 文字只在内存里；日志只记步骤号、耗时、结果码。调试抓取另做开关，默认关。
- **探针里的公开广播接收器不能进正式包。** 电脑调试命令只在 debug 构建里存在。

1. 侧载安装（浏览器或文件管理器）。
2. 安卓 13 起：应用信息 → 右上角菜单 → 允许受限制的设置。
3. 开启无障碍服务。
4. 电池：允许“后台高耗电”（vivo/iQOO 路径已验证；其他厂商的路径未验证，引导里先只写 vivo，遇到再补）。

7. 跑一次“体检”：依次启动三个任务涉及的 App，确认能读到首屏（不点任何东西）。

## 10. 未决与风险

- **用户协议**：开发期暂不处理，只在小号上测试（用户决定）；公开发布前仍需查清。
- **“最新消息”的定义（已定）**：“列表第一行”“聊天区最下面一条消息气泡”。是置顶会话、时间分隔条、撤回提示等情况时，按这条规则照做或停下说明原因。
- **App 更新与任务包分发（已定方向）**：App 只在用户点“检查更新”时联网，只连一个固定地址，下载的任务包必须通过签名校验；其余时间不发起任何连接。注意：安卓的联网权限是安装时一次性授予的，“只在更新时联网”是代码层面的承诺，系统不会强制。补救办法：开源代码供人审查；在引导里告诉用户可以用系统的“联网控制”（vivo 有按 App 关闭网络的开关）平时关掉网络。第 6 节第一条相应改为“只在用户主动检查更新时联网”。
- **跨机型**：先只在自己的手机（Neo5）上做，其他机型以后再验证。
- **微信 OCR 精度**：需要更多截图，M3 开始前先采一批（覆盖文字、图片、语音、表情、撤回、时间分隔条），统计准确率。
- **骨架的可插拔程度（已按调研定）**：见第 3 节“扩展点”。运行时代码插件、脚本引擎、后台监视器（用来自动关掉更新、权限弹窗）、路由图、模板匹配、截图上的区域编辑工具，都放到 v1 之后，届时逐项单独评估。
- **`takeScreenshot` 的最小调用间隔（2026-10-25 Neo5 实测）**：两次成功截图之间约 320–410 ms（首次 760 ms），间隔不够时系统直接拒绝（错误码 3）；单次截图 30–100 ms，首次约 400 ms。它决定微信步骤“找不到就重找”的最短间隔；M3 之前测出来。
- **测试夹具**：按 `fixtures/<app>/<screen>/<state>` 存脱敏后的树和截图（第一份 QQ 界面树进来时建）；`CoreTest.kt` 里的 `FakeDevice` 按“动作 → 下一帧”的脚本返回画面。每步的每个分支都要有用例，会进入等待的步骤要有多帧用例（照 OneDragon 的测试判据）。

### 多层回退时，前一层的数据要交给后一层

问题：gui-agent 的分层感知是先读 UIA，不够再重新截图做 OCR。两层各取各的，后一层既重复采集，也用不上前一层已经知道的东西。

做法：每一轮只建一个 `Frame`，各层往里追加，后面的层直接复用：

1. **树先读**，记录读取时刻。
2. 需要回退时才截图。截图存进同一个 `Frame`，并检查从读树到截图之间有没有界面变化事件。有的话重读一次树，保证两者描述的是同一个画面。
3. **树层把线索交给 OCR 层**：哪些容器有边界却没有文字（比如微信那个空节点、WebView 区域），OCR 就只裁这些区域；已经从树里读到文字的区域跳过。这样 OCR 的输入更小，也不会和树的结果重复。
4. OCR 结果按区域缓存在 `Frame` 里，同一轮的“找目标”和“查预期”共用。
5. 每一层没命中的原因（比如“树里有节点但没有文字”“OCR 置信度低”）也记进 `Frame`，既用于停下时给用户的说明，也进轨迹。

`Frame` 只在内存里，这一轮结束就丢弃；进轨迹的只有结构信息和耗时，不含截图和文字。
