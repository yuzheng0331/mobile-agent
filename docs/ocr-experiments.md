# OCR 实验记录

出成品前还要再做一轮优化，从这里接着做。每次实验记条件、结果、结论和重跑方法。这里只记数字，不记截图里的文字：截图和标注都在 `tools/probe/out/`，不进 git。

固定条件（没写明的都是这些）：

- 手机：vivo Neo5（骁龙 870，8 核 = 1 + 3 + 4），无线 adb。
- 模型：PP-OCRv6 small，fp32，官方 ONNX（版本和 SHA-256 见 `app/build.gradle.kts`）；onnxruntime 1.20.0。
- 手机测速截图：微信会话列表，深色模式，1080×2400，整屏检出 40 框。整屏检测输入是 1088×2400。
- 电脑：本机 Windows，onnxruntime 桌面版。电脑上的毫秒数只用来横向比较。

同一次（4 + 4）只识别下 1/4 屏：9 框，1173 ms。更早一次（同一截图、同样 4 线程）：整屏 4533 ms，下 1/4 屏 1181 ms，已知位置的单行只跑识别 50 ms，加载 408 ms，预热 1411 ms。

结论：

- 检测耗时只随检测线程数变，识别耗时只随识别线程数变，两段直接相加，线程数之间没有交互。两段都是 4 线程最快：6、8 线程会用上小核，反而慢。
- 识别推理占一半（2310 ms，51%），是最大的一块。检测推理 21%，检测预处理 18%。
- 检测预处理 796 ms 全是 Kotlin 的开销：缩放加归一化共 2.6 M 像素 × 3 通道，每个值单独写进 direct buffer，约 100 ns 一次。
- 解码 203 ms：每一步都要在 18710 个字符里取最大值。

## 4. 标准答案（2026-10-26）

- 来源：
  - 有界面树的截图（QQ、夸克等）用 `tools/probe/ocr_labels.py`，从树里可见的 `text` 节点生成标注。去掉的有：我们自己的悬浮条、带省略号的文字、只有标点的文字、小于 12 px 的框，以及框内像素亮度标准差小于 12 的（被遮罩或菜单盖住、截图上看不见）。这一步只看像素，不看 OCR 结果。
  - 微信的界面树是空的，4 张深色截图手工标注，另列 5 个“不该出现”的词：比如没有菜单的画面上不应读出“复制”。
- 规模：33 张截图，347 个标注，其中 ≤4 字的短标签 156 个；微信截图上 32 个；不该出现的词 5 个。
- 判分：
  - 标注框四周各放宽 10 px。和它重叠的框里有一个文字完全相同（去掉空白）就算读对；中心落在标注框内的几个框按阅读顺序拼起来相同，也算读对，对应 OCR 把一段字拆成几个框的情况。
  - 读错的短标签分两类：没有任何框重叠记“没框”，有框但文字不对记“认错”。
  - “误读”：不该出现的词在整张截图任何位置被读出来。
- 已知噪声：默认配置下“没框”的 7 个上一轮逐张看过，约 4 个是真漏（单个数字 ×2、被遮住一半的字 ×2），约 3 个是标注本身的问题；“认错”的 9 个还没归类。“全部”只有六成多，因为长文字（聊天内容、多行）要逐字完全一致，判得很严。任务找的是按钮这类短标签，以短标签为准。

## 6. 预处理改写（2026-10-26）

- 改了什么：检测和识别的缩放 + 归一化改为整行算进 `FloatArray` 再整块写入，行分 4 份并行；同一批里各行的 CTC 解码并行；推理输出少复制一次。运算和顺序不变。
- 准确率：电脑上复跑第 5 节，默认配置和每批 1 行的数字与改前完全相同（140/156，没框 7 / 认错 9；全部 234 和 236；微信 32/32；误读 0）。和 Python 版对照也不变：找到 98%，文字相同 89%。
- 电脑速度：默认配置从 1231 降到 829 ms/张，每批 1 行从 1357 降到 866 ms/张。

## 8. 手机：推理后端（2026-10-26，onnxruntime 1.20.0）

| 后端 | 结果 |
|---|---|
| NNAPI（检测和识别都用） | 跑了 9 组（最长边 × 每批），逐框和 CPU 相同（40/40、37/37），时间都在噪声范围内。大概率是整张图退回了 CPU：模型的输入尺寸可变，NNAPI 不接 |
| XNNPACK 只跑检测 | 输出和 CPU 相同（40/40），但检测推理 3098 ms，CPU 是 982 ms，慢了 3 倍；预热 3404 ms |
| XNNPACK 只跑识别 | 第一次推理就在 onnxruntime 原生代码里段错误（SIGSEGV），进程被杀；两次都复现 |

结论：两段都继续用 CPU。`OcrConfig` 的 `detProvider` / `recProvider` 留着，升级 onnxruntime 后用一条命令就能重测：桌面版和安卓版要一起升到同一版本。

## 9. 待测

## 重跑方法

- **标注**：
  - 生成：`python tools/probe/ocr_labels.py tools/probe/out/ocr_labels_tree.json <抓取目录> ...`，抓取目录里要同时有 `screen.png` 和 `tree.xml`。
  - 微信手工标注的格式：`{"file", "labels": [{"text", "box": [l, t, r, b]}], "absent": [...]}`。
  - 文件路径写绝对路径。
- **电脑准确率网格**：
  ```
  export OCR_LABELS="$(cygpath -aw tools/probe/out/ocr_labels_tree.json);$(cygpath -aw tools/probe/out/ocr_labels_wechat.json)"
  ./gradlew :core:test --tests '*OcrTest*grid*' --rerun -i
  ```
  - 只跑部分组合：设 `OCR_GRID`，例如 `boxThresh=0.6,side=1280;batch=1`。可用的键：`boxThresh`、`unclip`、`side`、`batch`。
  - 要加 `--rerun`，因为 Gradle 不跟踪环境变量。32 组约 20 分钟。
- **手机测速**：
  1. `./gradlew :app:assembleDebug`，再 `adb install -r`（手机亮屏时点“允许”）。
  2. 把截图推到 `/sdcard/Android/data/dev.phoneagent.app/files/ocr/screen.png`（Git Bash 下设 `MSYS_NO_PATHCONV=1`）。
  3. 启动测速页：`adb shell am start -W -n dev.phoneagent.app/.OcrBenchActivity -f 0x10008000`。不要用 `am force-stop`，它会关掉无障碍服务。
     - 默认跑三种后端（检测和识别同一种）× 最长边 × 每批，共 27 组。
     - 只跑一部分时加参数，例如 `--es providers CPU+CPU,CPU+XNNPACK --es sides 0,1280 --es batches 6`：`检测后端+识别后端`，`0` 表示原图。
     - 要逐框比对，就把 `CPU+CPU` 放在最前面。
     - 会崩的后端单独跑，因为原生崩溃会把整个进程带走。
  4. 读日志：`adb logcat -d -s PhoneAgent:I`。每组开始前会先记一行“开始 …”，崩了也能看出是哪一组。看到“测速结束”就是跑完了。
  5. 跑完删掉截图。等结果的脚本要按“测速结束”判断，不要按行数：上一次的等待脚本数到了“开始 …”那些行，提前删掉了截图。
  - 整个过程手机保持亮屏。刚覆盖安装完，无障碍服务要过几秒才重新绑定，这时启动的话，截图那一项会显示“未开启”。
