# 下一阶段需求的设计评审（2026-10-29）

Claude 主笔，Codex、DSH 各自独立回答同一份问题（问题和背景见文末），这里合并三方意见，并标出核对过的事实。三方都同意的结论直接写；有分歧的写明各自理由和我的建议。

**需要你决定的事**，正文里用 **【待定】** 标出来，文末有汇总。

## 0. 先说结论

| 需求 | 能不能做 | 一句话 |
|---|---|---|
| 1 管理员端 / 用户端，发布到网站，分发到微信 | 部分能 | 发布到网站能做。分发到微信建议改由网站后端用企业微信推送，不让手机去点“发送” |
| 2 低代码修包，上游更新和本机修改合并 | 能，有边界 | 网站接口和流程分开存；节点带稳定 id 和来源，按节点三方合并，冲突时不自动覆盖 |
| 3 去掉自然语言路由，参数加分支加有限循环 | 能 | 声明式分支和有上限的循环，不算脚本引擎。固定任务包运行时不需要模型 |
| 4 悬浮窗、通知、暂停、续跑、定时和自动触发 | 能，有系统限制 | 续跑要先让每一步的画面能被唯一认出；屏幕锁着（有密码）时什么都做不了 |
| 5 后台虚拟屏、性能分配、抢前台 | 部分能 | 必须经过 Shizuku（shell 身份）。安卓不能按屏幕分配 CPU / GPU，只能管住我们自己的消耗 |

## 1. 管理员端 / 用户端

### 1.1 版本怎么分

三方一致：**一个 APK，用角色区分**，不发两个安装包。“不需要登录”可以做到，但管理员身份必须有一个信任来源，不能是 App 里的隐藏开关。

- **管理员身份 = 一份签名的管理员配置。** 你签发给某个管理员，里面写着：他的网站域名、能用哪些管理员任务包、有效期。App 用内置公钥验签，验过才显示管理员功能。别人拿到 APK 也冒充不了管理员。
- **网站本身的鉴权还是网站的事。** 往网站发布内容要的 token 由管理员在 App 里填一次，存进 Android Keystore，不写进任务包，也不出现在日志里。这样冒充者即使拿到配置，没有 token 也发不出去。
- Codex 提醒的一点：签名只能证明“包是谁发的”，证明不了“现在拿着手机的是谁”。对团队内部使用，这样够了。

### 1.2 自动发布到管理员网站

两条路：

1. **调网站接口**（推荐，快而稳）：加一个 `http` 动作，只能连任务包里声明的主机，就像现在只能操作 `requires` 里的 App。参数来自任务包和用户填的值。
   **已定（2026-10-29，用户同意）**：这是 Phone Agent 自己发起联网，超出了原来不变量第一条的字面意思（“自己只为 App 更新和拉取任务包联网”）。不变量已改成“自己联网只做三件事：App 更新、拉取任务包、任务包声明过的自有网站接口”。新动作要过安全评审。
2. **在浏览器里点网站界面**：不碰不变量，但慢，网站改版就要修包。

接口怎么摸清：用 Rea 在电脑上抓（上一轮已经说过）。整理出来的接口表就是第 2 节的“站点适配层”。

### 1.3 收集用户截图，分发到微信指定账号

三方一致：**不要让手机去点微信的“发送”。**

- 自动发送违反不变量“动作集不含发送”。
- 网上对微信“自动发消息被封”的说法很多，但没有官方阈值，小号也照样可能被限制。
- 两个外部方案各有问题：DSH 建议预填好、停在发送键前由人点；Codex 建议转发先由用户手动完成。两个都安全，但都不是“自动”。

**我的建议：分发这件事根本不放在手机上做，让网站后端做：**

- 用户上传的截图和数据本来就在你们的网站上。网站后端可以直接用**企业微信的“消息推送”**（原群机器人）推到群里。这是 webhook 接口，免费，支持文本、Markdown、图片、图文；文档里有频率限制，常见的说法是每个机器人每分钟 20 条。
- 推给个人的话，用**服务号模板消息**，要认证服务号。
- 这样做是官方渠道，没有封号风险，也不碰手机端的任何不变量。还有一个关键好处：管理员的手机不用开着跑任务。
- 待核实：企业微信消息推送能不能发到有普通微信用户的外部群，网上说法不一，要用小号实测。

真要发到某个个人微信号、又不用企业微信的话，退路是 DSH 的方案：任务包打开会话、选好图片，停在“发送”前，悬浮面板提示“确认发送”，由人来点。

**隐私**（DSH 提的）：收集再转发用户的截图，属于处理个人信息，网站应该在用户上传时告知并取得同意。这是网站的责任，但公开发布前要查清。

## 2. 低代码修包，以及上游更新和本机修改的合并

### 2.1 任务包分三层

DSH 的分法我认同，再细化一下：

| 层 | 内容 | 谁改 | 多久改一次 |
|---|---|---|---|
| `site`（站点适配层） | 接口名 → 方法、路径、字段映射；网页表单的定位方式 | 上游（你） | 网站接口一变就改 |
| `flow`（行为图） | 步骤、分支、循环，只按名字引用 `site` 里的接口 | 上游加本机补教 | App 改版时改 |
| `params`（参数） | 用户填的网站参数 | 用户 | 首次运行时填 |

需求 2 里“上游更新只改网站接口”就变成**只换 `site` 层**：行为图只按名字引用接口，名字不变，本机学过的行为图一个字都不用动，也就不需要“自动修改行为图”。只有接口名或字段被删掉时，才需要改行为图；这种情况加载时就会校验出来，提示“这个包要更新”。

### 2.2 节点怎么标、怎么合并

三方方案基本一致：

- 每个节点（步骤、找法、预期）有稳定的 `id`，不用数组下标。节点记 `origin`（上游 / 管理员 / 本机补教）和 `base`（它基于哪个上游版本的哈希）。
- 本机修改存成**按节点 id 的补丁**，不复制整个包。现在的补教补丁顺势升级成这种形式。
- 上游发新版时做三方合并：基准是上次用过的上游版本，“本机”是补丁，“新上游”是新包：
  - 上游没改这个节点：保留本机补丁。
  - 上游改了、本机没改：用上游。
  - **两边都改了同一个节点：不自动合并**。DSH 的做法：两个版本都留着，运行时先认画面（`ScreenDef`）和 App 版本，挑能认出的那个；都认不出就停下，请用户补教。Codex 更保守：停用这一步，等用户选。我建议用 DSH 的做法，并在悬浮面板上提示“这一步本机改过，上游也改了”。
  - 上游删掉了本机改过的节点：本机补丁标成“孤儿”，不再生效，下次运行成功后清掉。
- 坐标类的补教要绑定屏幕尺寸、密度和 App 版本，任一项变了就提示“补丁可能失效”。现在已经绑了 App 版本。

### 2.3 低代码怎么做

Codex、DSH 都警告：UI 能任意改行为图，就成了脚本编辑器（违反不变量第 5 条）。所以编辑器只能组合**已注册**的找法、预期、动作、分支和循环，每次保存都走 `validate`。

我建议分两个入口：

1. **手机上：悬浮面板里的“重录这一步”**（给管理员和用户）。用户点一下正确的目标，App 根据点中的节点（文字、id、描述）或点击位置的 OCR 文字，自动生成找法候选，不只记坐标；确认后存成本机补丁。管理员可以把补丁导出成文件发给你，你审过、签名后，就成了上游版本。
2. **电脑上：probe 加 Claude Code 技能**（给你）。处理大的改版，这就是已经写进架构文档的“App 改版后修任务包”流程。网站接口变化用 Rea 抓，接口表自动生成 `site` 层的草稿。

管理员不直接签名发布：信任根只在你一个人手里，这和“任务包都由我来分发”一致。管理员多了以后，可以给每个管理员发一张由你的根密钥签过的证书，只允许他签自己网站域名的 `site` 层。这一步可以以后再做。

## 3. 去掉自然语言路由；参数、分支、有限循环

### 3.1 自然语言路由

同意去掉：固定任务包就用按钮、桌面快捷方式和小组件，一键启动。`aliases` 和 `Router` 可以先留着不接界面，以后要语音入口时再说。

### 3.2 “运行时完善行为图”的表达方式

三方一致：能做，而且不必打破“不做脚本引擎”。条件是**表达力只做有限的枚举**：

- `params`：任务包声明有类型的参数（文本、数字、单选，可带校验），首次运行时填，存在本机。
- `when`：`{字段, 比较, 值}`。比较只有白名单里的几种：等于、不等于、包含、存在、大于、小于。字段只能来自接口返回值、上一步找到的内容或参数。不支持算术、嵌套表达式和赋值。
- `forEach`：`{over: 一个列表找法或一个接口返回的列表, max: ≤50, body: [...]}`，对每一项执行同一段步骤。
- 每个分支有步数上限，整个包有总步数上限和总时长上限。这些上限在加载时就能算出来，校验能拒收超限的包。
- 不支持 `while`、递归、变量赋值，也不支持按字符串动态选动作名。

“运行时完善”就是 DSH 说的**模板展开**：拿到这个用户的表单和数据后，把分支和循环展开成一份本次的执行计划，跑完就丢掉。只有用户补教过，才写回本机补丁。

两个连带的点：

- 走网站接口时，参数直接放进请求，不需要“文字输入”动作。走网页界面时，就需要一个 `type` 动作，要先过安全评审。
- 循环的断点（见第 4 节）只记第几项，不记内容。

### 3.3 学习模式还要不要模型

三方一致：**固定任务包运行时不需要模型。** OCR 加规则更快，结果也可预测；整屏 OCR 已经要 3 秒左右，再加模型只会更慢。

模型仍有价值的地方都不在运行时，也都不违反“不靠云端”：

1. **写包和修包**：在电脑上用 Claude Code 把 probe 抓到的界面整理成任务包草稿。这是开发工具，不是 Agent 的一部分。
2. **兜底**：所有找法都没命中、用户又不想补教时，本机 VLM 给出 1–3 个候选位置让用户选，默认关闭。Neo5 上跑 2B 级别的 VLM，单张图要好几秒，还要占 2–3 GB 内存，所以先只在 `Finder` 注册表里留一个 `vlm` 位置，不实际接入。
3. **字段对应**：把网站表单上的标签（“联系电话”）对应到参数（“手机号”）。先用同义词表就够了。

## 4. 悬浮窗、通知、暂停、续跑、触发

- **悬浮面板**：用 `TYPE_ACCESSIBILITY_OVERLAY`，不用申请悬浮窗权限（M4 已在计划里）。完成或失败时发通知，Android 13 需要 `POST_NOTIFICATIONS` 运行时权限。
  更正一处 DSH 的说法：`attachAccessibilityOverlayToDisplay` 是 Android 14（API 34）才有的，不是 API 30。Neo5 已升级到 14（2026-10-29），可以用：面板能挂到指定屏，虚拟屏上也能标出“将要点哪里”。
- **暂停 / 续跑**：只在步骤之间暂停。检查点只存任务包 id 和版本、步骤 id、循环第几项、参数，不存任何界面内容，符合不变量。续跑前先认画面。
  DSH 指出的地基问题我同意：现在的 `expect` 太宽，比如“聊天设置”在任何聊天页都成立，直接续跑可能在错的会话里复制、还报成功。**所以要先给每一步加上能唯一认出的 `screen`（ScreenDef）。** 续跑、合并冲突时选版本、失败归因，都靠它。
- **定时**：
  - 精确时间用 `setExactAndAllowWhileIdle`，需要 `SCHEDULE_EXACT_ALARM`，要引导用户去开“闹钟和提醒”。Android 14 起新装的 App 默认是拒绝的；Neo5 现在是 13。
  - 不要求准点的，用 WorkManager：一次性任务可以任意延迟，周期任务最短 15 分钟。
  - **硬限制**：无障碍要在屏幕亮着、已解锁时才能操作 App。有锁屏密码时，到点只能发一条通知：“到点了，解锁后点这里开始”。我们不能、也不该绕过锁屏。
- **自动触发**：按成本从低到高：
  - 时间；
  - 充电或断电；
  - 连上某个 Wi-Fi；
  - 打开某个 App：无障碍本来就收得到窗口事件，几乎零成本。
  - 收到某条通知：DSH 建议用 `NotificationListenerService`，只按包名或关键词判断，正文不进日志。**已定（2026-10-29）**：用户同意对微信、QQ 做通知监听，取代原来“通知监听不做”的决定。
- **会改东西的步骤**（发布、上传）由自动触发启动时，Codex 建议先在面板上请用户确认一次。我同意，至少在刚开始的几个版本里这样做。

## 5. 后台虚拟屏

### 5.1 能不能做（核对过）

- **普通 App 做不到**：按 AOSP 的 activity 启动策略，Android 10 起，第三方 App 只能把**自己的** Activity 启动到自己建的虚拟屏上；要启动别的 App，需要系统权限。
- **shell 身份能做到**：scrcpy 的 `--new-display --start-app`，以及开源项目 headless-android，都是用 shell 身份（Shizuku 或 adb）建屏，再用 `am start --display` 启动 App。headless-android 支持 Android 10 以上，需要 Shizuku，**用的时候手机要解锁**。
- **无障碍在虚拟屏上能用的部分**（API 30 起都有）：
  - 按屏截图：`takeScreenshot(displayId, …)`；
  - 按屏手势：`GestureDescription.Builder.setDisplayId`，官方文档写着 API 30 加入。DSH 说“不确定能不能落到虚拟屏”，接口是存在的，但对 shell 建的屏是否生效要真机测；
  - 读所有屏的窗口：`getWindowsOnAllDisplays`。
- **更快的取帧方式**：用我们自己的 `ImageReader` 当虚拟屏的输出画面。取帧不受 `takeScreenshot` 最小间隔（约 0.35 s）的限制，还省掉一次截图。headless-android 就是这么做的。

### 5.2 代价和坑

- **授权链更长**：要装 Shizuku，用无线调试启动；手机重启后要重新启动 Shizuku。这是新用户最容易流失的一步，所以虚拟屏只做成可选的进阶功能。
- **抢焦点**：DSH 指出，避免抢主屏焦点要靠 `OWN_FOCUS` 一类的虚拟屏标志，而这一类标志在 Android 14 前后才出现（具体 API 级别我没查到官方说明）。**Neo5 上的 Android 13 很可能会出现“在虚拟屏启动 App，主屏焦点被切走”，必须真机测。**
- **同一个 App 不能同时在两块屏上**（我补充的）：用户在主屏上打开微信，会把任务所在的界面拉回主屏。检测到这种情况就暂停任务、发通知，不要跟用户抢。
- **加速输入法和后台模式冲突**（我补充的）：现在跑 OCR 任务时会临时切到我们的无键盘输入法，以拿到大核。后台模式下用户正在用手机，切走他的键盘会让他打不了字。**所以后台模式不能切输入法**，只能接受 0–5 号核。按 `docs/ocr-experiments.md` 4.9 的实测，这样检测会慢约一倍，GPU 识别慢约 30%。
- **微信在虚拟屏上**：DSH 的判断是能跑，但视频、语音、相机大概率不可用；带 `FLAG_SECURE` 的页面（比如支付）截出来是黑的；App 能读到自己不在 0 号屏上。会不会因此被风控，没人能保证，只能用小号实测。抖音、小红书排在微信之后测。
- **不变量第二条**（只操作 `requires` 里的 App）在多屏下要按屏判断：前台包名要带 `displayId`。

### 5.3 性能分配

三方一致：**安卓没有按屏幕分配 CPU / GPU 的接口**。vivo 的核分组是厂商定死的，第三方 App 改不了别的 App 的调度。能做的只有管住我们自己：

- 虚拟屏用较低的分辨率（比如边长减半，像素只剩 1/4），尽量降低刷新率。
- 根据 `PowerManager.getThermalHeadroom`（API 30）和前台 App 的类别（比如游戏）自动收缩：OCR 少开线程、选 CPU 还是 GPU、降低识别频率；发热到一定程度就暂停。
- 一次只跑一个任务。
- 真正能用的场景是“手机亮着、用户在做别的事”。这时的性能冲突，只能靠上面的自适应收缩来缓解。

## 6. 额外的优化建议（让管理员和用户都免费、省事）

- **分发零成本**：任务包和 App 更新放在静态文件托管（对象存储加 CDN，或 Gitee / GitHub Releases），靠签名保证安全，不需要你自己维护服务器。
- **一键体检**：运行前检查：任务包签名、App 版本是否在 `testedWith` 里、需要的权限（无障碍、后台高耗电、通知、闹钟）是否都开了。缺什么就直接跳到对应的设置页。
- **失败反馈只传结构**：失败时用户可以主动导出一份**只含结构和耗时**的轨迹（不含文字和截图），发给管理员。是否允许发出，由用户每次点击决定。
- **管理员看板放在网站上**：用户跑完的成功或失败次数，可以通过任务包里的 `http` 步骤报给管理员网站，只报次数和错误码。这同样要等 1.2 节的【待定】有结论。

## 7. 优先级

三方的前三名有重合，合起来排：

1. **每一步加唯一的 `screen` 识别，并做“按状态继续”**：续跑、合并、失败归因都靠它（DSH 第 1，Codex 第 3）。
2. **任务包分层（`site` / `flow` / `params`），节点带 id 和来源，写合并器**：先只在电脑上用测试跑通，不做界面（DSH 第 2）。
3. **悬浮面板加补教，加“重录这一步”**：所有需要人确认的环节都在这里，包括发送前确认、发布前确认（DSH 第 3，M4 原计划）。
4. 声明式的 `params` / `when` / `forEach`，加上静态上限校验（Codex 第 2）。
5. 管理员签名配置，加 `http` 动作（等不变量的决定）。
6. 定时和自动触发。
7. 虚拟屏（最后做，先在 Neo5 上做可行性小实验：抢焦点、`setDisplayId` 手势、微信能不能跑）。

## 8. 明确不做

### R1 补教：从“一个点”变成“一个元素”

补教时用户点一下，App 不只记坐标，而是把这一下**解析成一个元素**，并补上前置和预期。

1. **抓那一刻的帧**：读界面树；需要时截图。
2. **生成候选找法**，按下面的顺序：
   1. **界面树**：取点击位置下最小的可点节点，记下它的 id、文字、描述、类名，加上最近一个带 id 或文字的祖先、它在兄弟节点里的序号，组成一份多属性“指纹”。从指纹里挑出在当前帧上**只命中这一个节点**的组合，作为候选找法（`id`、`text` 加 `exact`、`listItem` 加 `in`……）。
   2. **反查已注册的找法**：把适用的找法（`chatRow`、`lastBubble`、`ocrText`……）在这一帧上都跑一遍，命中框盖住点击位置的就是候选。微信这类界面树为空的 App 靠这一条。好处是代码里以后新加的找法，补教自动就能用上。
   3. 都没有时才用坐标（按屏幕比例存）。
3. **请用户确认**：面板上高亮命中的框，用户确认后才保存。用文字认元素的候选要用户明确确认，免得把联系人名、消息内容当成定位存进本机（不变量：界面内容不落盘）。
4. **前置和预期，也就是怎么接上后面的步骤**：
   - 前置：当前画面，即上一步的 `expect` 或认出的 `screen`。
   - 预期：**下一步的找法能命中**。补教点完后，解释器照常走下一步；下一步找到了，就说明这一下接上了，于是把“下一步的目标出现了”记成这一步的预期。为此新增一种预期 `canFind: <下一步 id>`，引用下一步的找法，不复制一份。同时把点完后新出现、消失的界面文字（菜单项、标题）列为候选预期，用户可以勾选。
   - 下一步还是找不到，说明中间少了一步（比如新出现的弹窗）。面板提示“再点一下”，继续录，直到下一步能命中为止；录的每一下都作为新节点插进去。这就是“插入步骤”的补教，也是演示录制的最小形式。
5. **什么时候要重补**：运行时先用存下的找法找。找不到时，用指纹做**相似度匹配**：id 相同但文字变了、文字相同但 id 变了、同一位置的同类节点。相似度够高就用，并在面板上提示“已自动修复，请确认”；不够就停下请补教。Selenium 生态的 Healenium、研究工作 Erratum（用树匹配修复失效的网页定位）都是这个思路。
6. **绑定什么**：元素型补丁记下当时的目标 App 版本，只用来提示，不会因为版本变了就失效。坐标型补丁绑定目标 App 版本和屏幕尺寸，任一项变了就不再使用（现在的补教补丁已经绑了目标 App 版本，不是 Agent 的版本）。

### R2 管理员端任务包编辑器（2.3），以及网站改版修包（1.2.2）

**编辑器形态**：手机上用**分层列表**，不用画布流程图。iOS 快捷指令、MacroDroid 都是这种做法：一行一个动作，分支和循环是可折叠的块。小屏幕上拖线连节点很难用。以后要在电脑上看图形视图，也读写同一份 JSON。

- **节点卡片**：每个节点一张卡，内容是动作、找法（可以多个，按顺序）、预期、超时，都从下拉里选已注册的名字。
- **界面由注册表生成**：`Builtins` 里的每个找法、预期、动作都带一份说明：中文名、参数和类型、需要的能力（如 `ocr`）。编辑器照着这份说明画表单。代码里新加一个找法，编辑器自动多一个选项，不用改界面。
- **节点操作**：在前面插、在后面插、修改、删除、拖动排序、复制、包进分支或循环。
- **录**：卡片上点“重录”，编辑器缩成悬浮面板并切到目标 App，点一下，走 R1 的流程生成找法和预期，然后回到卡片。点“录一段”可以连续录多步。
- **测**：
  - “试找”：不做动作，只在目标 App 上把这一步找法命中的框画出来。
  - “只跑这一步”。
  - “从这一步跑到底”：先认画面，认对了才跑。
  - 每次修改都实时跑 `validate`，错误直接标在卡片上。
- **版本**：每次保存是一个本机版本；“和上游比较”显示差异；“发布”就是用管理员密钥签名，再上传到管理员的网站。
- **接口页**：列出 `site` 层的每个接口，可以“测试调用”看返回了哪些字段；可以从网站的 OpenAPI 说明导入并对比差异；也可以导入电脑上用 Rea 生成的接口表（文件或二维码）。

**网站改版时怎么修最省事**：管理员就是网站的管理者，所以最有效的一招是**让网站在固定地址提供一份机器可读的接口说明（OpenAPI）**，大多数后端框架能自动生成。有了它：

1. **对比**：App 拉任务包时顺便拉这份说明，和 `site` 层对比。字段改名、路径变了这类能对上的变化，自动生成修改建议，管理员在接口页点“测试”，通过后发布。
2. **运行时检测**：接口返回的字段和 `site` 层声明的对不上时，当场停下，说清是哪个接口、哪个字段，不让它在后面某一步莫名失败。管理员点通知，直接跳到编辑器里的这个接口。
3. **没有 OpenAPI 的网站**：在电脑上用 Rea 抓，生成 `site` 层再导入。

### R3 合并（2.2）

上游就是管理员，节点的 `origin` 取值是：管理员（上游）、本机补教。合并规则按第 2.2 节 DSH 的做法：两边都改了同一个节点时，两个版本都留下，运行时按认画面和 App 版本挑一个，都不中就停下请补教。R1 的元素型补丁让“两边都改了”的情况少很多：管理员只改了网站接口，本机补的是 App 界面上的元素，两者不碰同一个节点。

### R4 变量和表达式（3.2）

你说得对：循环由网站数据决定，一定有限。保留 `max` 上限不是怕死循环，而是防网站出 bug，比如一次返回一万行，Agent 就发布一万次。建议保留这个上限，由管理员设，默认值放宽。

第一轮不做变量和表达式，理由有三：
1. **不变量第 5 条“不做脚本引擎”**：图灵完备的表达式能写出任意逻辑，任务包就无法在加载时被校验，跑多久、会点什么、会连哪里都算不出来。
2. **签名只证明“是谁发的”，不证明“写对了”**：管理员现在能自制任务包，逻辑越强，写错的后果越大。
3. **有了 `http` 动作以后的新风险**：变量能把**屏幕上读到的内容**搬进发给网站的请求，这正是不变量第一条禁止的。

但你的需求确实要“取值、拼接、比较”，所以建议**做受限版本**：
- **变量**：单次赋值。一步用 `save: 名字` 存下接口返回的字段、循环当前项或找法命中的结果；后面的步骤用 `{名字}` 引用。存下后不能改写。
- **表达式**：只用一个**非图灵完备**的固定子集：比较，与、或、非，包含，字符串拼接和模板，数字加减，长度，日期格式化。没有循环和自定义函数，求值时间和表达式长度成正比。Google 的 CEL（Common Expression Language）就是按这个思路设计的：线性时间、没有副作用、非图灵完备。我们照它的子集自己实现，不引入整套依赖。
- **来源标记**：从界面（树、OCR）取到的值带“界面”标记，不能进 `http` 请求，只能用在本机的点击和输入里。接口返回的值和用户参数没有这个限制。
- **加载时校验**：变量先定义后使用、类型对得上、`http` 的主机在声明和证书范围里（R6）、带界面标记的值没有流进请求。任何一条不满足就拒收。

这要把不变量第 5 条从“不做脚本引擎”改成“不做脚本引擎；表达式只用非图灵完备的固定子集，界面上读到的值不能进网络请求”。**【待定】**等你点头。

### R5 应用分身、VLM 兜底、自动适应接口变化（第 8 节）

- **应用分身**：DSH 说的“不做”，指的是**改包名、重签名**去克隆微信：微信会校验签名，必然失败，还会触发风控。**系统自带的分身**是另一回事：Android 12 引入了系统的克隆用户（clone profile），Android 14 正式开放 App 克隆，分身装在单独的用户里，数据和本体隔离。第 0 关在 Android 13 上按 Intent 启动分身失败；升级到 14 后值得重试：
  1. 用 `LauncherApps` 列出分身所在的用户；
  2. 用 `startMainActivity(组件, 用户)` 启动；
  3. 确认无障碍服务能读到分身窗口的界面。

  这是一个小实验，大约半天。vivo 的分身是不是走 AOSP 的 clone profile，还不知道。
- **VLM 兜底**：你说得对，第一轮第 8 节“运行时不调用 VLM”和 3.3 的兜底矛盾，已改成：**正常路径不调用；失败时可选兜底（默认关），在本机跑**。和 R1 接起来：VLM 给出候选位置，用户确认后，走补教流程转成元素型找法存下来。这样同一个问题 VLM 只用一次，以后靠找法，不会每次都慢。本机模型选 GUI 定位专用的小模型（如 ShowUI-2B、UI-TARS 2B 一类），比通用 VLM 更合适；Neo5 上一张图估计要数秒到十几秒，需要实测。
- **自动适应接口变化**：“任意”做不到。字段被删了，或者语义变了（比如“金额”从元改成了分），机器猜错就会把错的数据发布出去，而且没有任何报错。能做的是**自动检测加半自动修复**（R2）：能对上的改名和路径变化自动生成修改建议，测试通过后再发布。

### R6 Android 14 和信任模型

**Neo5 升级到 Android 14 带来的变化**：
- `attachAccessibilityOverlayToDisplay`（API 34）可以用了。
- 精确闹钟：14 起新装的 App 默认没有 `SCHEDULE_EXACT_ALARM`，安装引导里要带用户去“闹钟和提醒”打开。
- 前台服务：14 起必须声明类型（`foregroundServiceType`），以后用到前台服务时注意。
- 通知监听：要用户在“通知使用权”里打开。侧载的 App 从 13 起，和开无障碍一样，要先“允许受限设置”。微信、QQ 的通知里有消息正文，只在内存里按包名和关键词匹配，日志只记“触发了几次”。

**信任模型**：
- **证书链**：你的根密钥（离线保管）签发管理员证书。证书里写管理员公钥、名字、他自己网站的域名，不设有效期。管理员用自己的私钥签任务包，用户的 App 验证这条链。
- **管理员能做什么**：在本机修改、自制任务包；本机还没签名的包只能在他自己的手机上跑。签名后上传到自己的网站，分发给他的用户。
- **用户怎么订阅，不用登录**：扫管理员给的二维码，里面是网站地址和证书指纹。第一次订阅时，App 显示“这个管理员的任务包会操作哪些 App、连哪些网站”，用户同意后才装。
- **永久证书的两个补救**，**【待定】**等你同意：
  1. **撤销列表**：证书不过期，但私钥丢了要能作废。撤销列表用根密钥签名，随 App 更新或拉任务包时一起拉下来。
  2. **域名范围**：管理员签的包里，`http` 只能连证书里写的域名。这样“只连自有网站”这条不变量由验签来保证，而不是靠管理员自觉。

1. **受限的变量和表达式**（R4）：单次赋值、非图灵完备的固定子集、界面值不能进网络请求，并据此改不变量第 5 条的措辞。
2. **管理员证书的撤销列表和域名范围**（R6）。
