## 1. 角色与信任

**已定：一个 APK，角色由证书决定。**

- **证书链**：你的根密钥（离线保管）签发管理员证书。证书里只有管理员公钥和名字，**不限域名、永久有效**。管理员用自己的私钥签任务包，用户的 App 验证这条链。
- **管理员能做什么**：在本机修改、自制任务包，没签名的只能在自己手机上跑；签名后上传到自己的网站，分发给他的用户。
- **用户怎么订阅（不登录）**：扫管理员给的二维码，里面是网站地址和证书指纹。第一次订阅时，App 列出“这些任务包会操作哪些 App、连哪些网站”，用户同意才装。
- **永久证书的补救**：
  - **撤销列表**：用根密钥签名，随 App 更新和拉任务包时一起拉。私钥丢了，证书照样能作废。
  - **不限域名的补救**：任务包更新后，要连的主机比上一版多了，App 先列出新主机，用户同意后才装。“只连自有网站”由管理员负责，用户每次都看得到、能拒绝。
- **网站自己的鉴权**：往网站发布要的 token，由管理员在 App 里填一次，存进 Android Keystore，不写进任务包，也不进日志。
- 签名只证明“包是谁发的”，证明不了“现在拿着手机的是谁”。团队内部使用，这样够了。

## 2. 联网与网站接口

**已定：不变量第一条扩到自有网站接口。** Phone Agent 自己联网只做三件事：App 更新、拉取任务包、调用任务包声明过的自有网站接口。界面上读到的内容不能填进这些请求。被操作的 App 或网站自己发出的数据（登录、上传图片等），是它们自己的事。

- **`http` 动作**：只能连任务包 `site` 层里声明的主机，就像现在只能操作 `requires` 里的 App。新动作要先过安全评审。
- **`site` 层（站点适配层）**：写明每个接口的方法、路径、参数，以及**返回结构**：列表在哪、有哪些字段、各是什么类型。加载时就能校验后面的步骤有没有用错字段。
- **接口怎么摸清**：团队的网站没有文档时，在电脑上用 Rea 抓真实请求，生成 `site` 层的草稿。

**建议：网站改版时这样修最省事。** 管理员就是网站的管理者，最有效的一招是让网站在固定地址提供一份机器可读的接口说明（OpenAPI），大多数后端框架都能自动生成。

1. **对比**：App 拉任务包时顺便拉这份说明，和 `site` 层对比。字段改名、路径变了这类能对上的变化，自动生成修改建议；管理员在编辑器的接口页点“测试”，通过后发布。
2. **运行时检测**：接口返回的字段和 `site` 层声明的对不上时当场停下，说清是哪个接口、哪个字段，免得到后面某一步莫名其妙地失败。管理员点通知，直接跳到编辑器里的这个接口。
3. **没有 OpenAPI 的网站**：用 Rea 重抓，导入新的 `site` 层。

**为什么不做“自动适应任意接口变化”**：字段被删了，或者语义变了（比如“金额”从元改成了分），机器猜错了，就会把错误的数据发布出去，而且不报任何错。所以只做“自动检测 + 半自动修复 + 测试后发布”。

## 3. 任务包结构

### 3.1 三层

| 层 | 内容 | 谁改 | 什么时候改 |
|---|---|---|---|
| `site` | 接口名 → 方法、路径、参数、返回结构；网页表单的定位方式 | 管理员 | 网站接口变了 |
| `flow` | 行为图：步骤、分支、循环，只按名字引用 `site` 里的接口 | 管理员，加上本机补教 | App 改版、补教 |
| `params` | 用户填的初始参数（文本、数字、单选，可带校验） | 用户 | 首次运行时 |

上游只改网站接口时，换掉的只是 `site` 层；行为图按名字引用接口，名字不变，本机学过的行为图一个字都不用动。接口名或字段被删了，加载时会校验出来，提示“这个包要更新”。

### 3.2 变量、表达式、分支、循环（已定）

- **变量单次赋值**：一步用 `save: 名字` 存下接口返回的数据、循环当前项或找法命中的结果；后面的步骤用 `{名字}` 引用，不能改写。循环每一轮是新的作用域，所以每轮重新绑定当前项不算改写。
- **表达式只用非图灵完备的固定子集**：比较；与、或、非；包含；字符串拼接和模板；数字加减；长度；日期格式化。没有循环和自定义函数，求值时间和表达式长度成正比。照 Google CEL（Common Expression Language）的思路，自己实现其中一个子集，不引入整套依赖。
- **`when`**：条件成立才执行一段步骤。
- **`forEach`**：对一个列表的每一项执行同一段步骤，通常是接口返回的列表。实际循环几次由数据决定；`max` 只是防网站出错的安全上限（比如一次返回一万条，就会发布一万次），由管理员设。
- **来源标记**：从界面（树、OCR）取到的值带“界面”标记，只能用在本机的点击和输入里，放进 `http` 请求会被拒收。接口返回的值和用户参数没有这个限制。
- **加载时校验**：变量先定义后使用、字段存在、类型对得上、`http` 主机在声明里、界面值没流进请求、按各层 `max` 算出的最大步数没超限。任何一条不满足，整个包就拒收，不会跑到一半才失败。
- 不做 `while`、递归，也不做按字符串动态选动作名。

**为什么只做受限版**：图灵完备的表达式能写出任意逻辑，任务包就没法在加载时校验：跑多久、会点什么、会连哪里，都算不出来。签名只保证“是谁发的”，不保证“写对了”。另外，有了 `http` 以后，不受限的变量能把屏幕内容搬进网络请求。

**例子：接口返回 5 组数据，每组取几个字段，循环 5 次，把字段值注入每轮的参数。**

```json
"site": {
  "host": "admin.example.com",
  "endpoints": {
    "pendingPosts": {
      "method": "GET", "path": "/api/posts?status=pending&group={groupId}",
      "returns": {"list": "data.items",
                  "fields": {"id": "string", "title": "string", "body": "string", "price": "number", "images": "list<string>"}}
    },
    "markPublished": {"method": "POST", "path": "/api/posts/{id}/published"}
  }
}
```

```json
{"id": "fetch", "do": "http", "call": "pendingPosts", "save": "posts"},
{"id": "eachPost", "forEach": "posts", "as": "p", "key": "p.id", "max": 50, "body": [
  {"id": "label", "let": {"caption": "p.title + ' · ¥' + string(p.price)"}},
  {"id": "pick", "when": "p.price > 0 && size(p.images) > 0", "then": [
    {"id": "open", "do": "tap", "target": {"find": [{"text": "{p.title}", "exact": true}]}}
  ]},
  {"id": "done", "do": "http", "call": "markPublished", "with": {"id": "{p.id}"}}
]}
```

- **注入**：循环体里任何参数都能用 `{p.字段}` 引用当前这一组，也能用 `let` 算出新值（比如 `caption`）再引用。
- **嵌套**：组里还有列表（比如 `images`）时，可以再套一层 `forEach`，最大步数按两层 `max` 的乘积算。
- **断点不重复**：`key` 标出每组的唯一标识，断点只记已完成组的 key，不记内容。续跑时重新调接口、跳过已完成的组，同一组不会发两次。
- 走网站接口时，参数直接放进请求，不需要“文字输入”动作；走网页界面时才需要 `type` 动作，要先过安全评审。

### 3.3 节点的身份

每个节点（步骤、找法、预期）都有稳定的 `id`，不靠数组下标。节点记两样东西：`origin`，取值是管理员（上游）或本机补教；`base`，即它基于哪个上游版本的哈希。合并（4.3）和续跑（5.2）都靠这两样。

## 4. 学习与修包

### 4.1 补教：认元素，不只记一个点（建议）

用户在补教时点一下，App 把这一下解析成**一个元素**，并补上前置和预期。

1. **抓那一刻的帧**：读界面树，需要时截图。
2. **生成候选找法**，按顺序：
   1. **界面树**：取点击位置下最小的可点节点，记下它的 id、文字、描述、类名，加上最近一个带 id 或文字的祖先，以及它在兄弟节点里的序号，组成一份多属性“指纹”。从指纹里挑出在当前帧上**只命中这一个节点**的组合，作为候选找法。
   2. **反查已注册的找法**：把适用的找法（`chatRow`、`lastBubble`、`ocrText`……）在这一帧上都跑一遍，命中框盖住点击位置的就是候选。微信这类界面树为空的 App 靠这一条；代码里以后新加的找法，补教也自动能用。
   3. 都没有，才存坐标（按屏幕比例存）。
3. **请用户确认**：面板上高亮命中的框，用户确认后才保存。靠文字认元素的候选要用户明确确认，免得把联系人名、消息内容当作定位存进本机（不变量：界面内容不落盘）。
4. **前置和预期，也就是怎么和后面接上**：
   - 前置：当前画面，即上一步的 `expect` 或认出的 `screen`。
   - 预期：**下一步的找法能命中**。补教点完后，解释器照常走下一步，找到了就说明接上了，于是新增一种预期 `canFind: <下一步 id>`，直接引用下一步的找法。点完后新出现或消失的界面文字（菜单项、标题），也列为候选预期，让用户勾选。
   - 下一步仍然找不到，说明中间少了一步（比如新出现的弹窗）：面板提示“再点一下”，一直录到下一步能命中为止，录下的每一下都作为新节点插进去。
5. **什么时候要重补**：运行时先用存下的找法找；找不到，再用指纹做**相似度匹配**（id 相同但文字变了、文字相同但 id 变了、同一位置的同类节点）。够像就用，并提示“已自动修复，请确认”；不够像就停下，请用户补教。Selenium 生态的 Healenium、研究工作 Erratum（用树匹配修复失效的网页定位）都是这个思路。
6. **绑定什么**：元素型补丁记下当时的目标 App 版本，只用来提示，不会因为版本变了就失效。坐标型补丁绑定目标 App 版本和屏幕尺寸，任一项变了就不再使用。

### 4.2 管理员端编辑器（建议）

- **形态**：手机上用**分层列表**，不用画布流程图：一行一个动作，分支和循环是可折叠的块（iOS 快捷指令、MacroDroid 都是这样）。小屏幕上拖线很难用。以后要在电脑上看图形视图，也读写同一份 JSON。
- **节点卡片**：动作、找法（可以有多个，按顺序试）、预期、超时，都从下拉里选已注册的名字。
- **界面由注册表生成**：`Builtins` 里每个找法、预期、动作都带一份说明（中文名、参数和类型、需要的能力），编辑器照着它画表单。代码里新加一个找法，编辑器自动多一个选项。
- **节点操作**：在前面插、在后面插、修改、删除、拖动排序、复制、包进分支或循环。
- **录**：卡片上点“重录”，编辑器缩成悬浮面板并切到目标 App，点一下就按 4.1 的流程生成找法和预期，然后回到卡片。“录一段”可以连续录多步。
- **测**：
  - “试找”：不动作，只在目标 App 上画出这一步找法命中的框。
  - “只跑这一步”。
  - “从这一步跑到底”：先认画面。
  - 每次修改都实时跑 `validate`，错误直接标在卡片上。
- **接口页**：列出 `site` 层的接口，可以“测试调用”看返回的字段，可以导入 OpenAPI 对比差异，也可以导入 Rea 生成的接口表（文件或二维码）。
- **版本**：每次保存是一个本机版本；“和上游比较”显示差异；“发布”就是用管理员密钥签名，再上传到管理员网站。

电脑上还有另一个入口：probe 加 Claude Code 技能，处理 App 的大改版（ARCHITECTURE 第 8 节“App 改版后修任务包”）。

### 4.3 上游更新和本机修改的合并（已定，DSH 的做法）

本机修改存成**按节点 id 的补丁**，不复制整个包。上游发新版时做三方合并：基准是上次用的上游版本，一边是本机补丁，一边是新上游。

| 情况 | 处理 |
|---|---|
| 上游没改这个节点 | 保留本机补丁 |
| 上游改了，本机没改 | 用上游 |
| **两边都改了同一个节点** | 两版都留。运行时按认出的画面和 App 版本挑一个，都不中就停下请补教；面板提示“这一步本机改过，上游也改了” |
| 上游删了本机改过的节点 | 本机补丁标为“孤儿”，不再生效，下次运行成功后清掉 |

元素型补教让“两边都改”少了很多：管理员通常只改网站接口，本机补的是 App 界面上的元素，两者碰不到同一个节点。

### 4.4 模型（已定）

- **正常路径不用模型**：固定任务包靠 OCR 加规则，更快，结果也可预测。整屏 OCR 已经要 3 秒左右，再加模型只会更慢。自然语言路由去掉，改成按钮、桌面快捷方式和小组件一键启动；`aliases` 和 `Router` 先留着，不接界面。
- **失败时本机 VLM 兜底**（可选，默认关）：所有找法都没命中、用户又不想补教时，VLM 给出 1–3 个候选位置；用户选中后，按 4.1 转成元素型找法存下来。同一个问题 VLM 只用一次，以后靠找法。候选模型选 GUI 定位专用的小模型（ShowUI-2B、UI-TARS 2B 一类），Neo5 上每张图预计数秒到十几秒，要实测。
- **写包、修包**：在电脑上用 Claude Code 把 probe 抓到的界面整理成草稿。这是开发工具，不属于 Agent。
- **表单字段对应**（比如“联系电话”对应“手机号”）：先用同义词表。

## 5. 运行体验

### 5.1 悬浮面板和通知（建议）

- 面板用 `TYPE_ACCESSIBILITY_OVERLAY`，不用申请悬浮窗权限（M4 已在计划里）。Neo5 已升级到 Android 14，可以用 `attachAccessibilityOverlayToDisplay`（API 34）把面板挂到指定的屏，虚拟屏上也能标出“将要点哪里”。
- 完成或失败时发通知，需要 `POST_NOTIFICATIONS` 运行时权限。
- 所有需要人确认的环节都在面板上：补教、重录、发布前确认。

### 5.2 暂停和续跑（建议）

- 只在步骤之间暂停。检查点只存任务包 id 和版本、步骤 id、循环里已完成的 key、参数，不存任何界面内容。
- **前提**：每一步都要能被**唯一认出**（`screen`，即 ScreenDef）。现在的 `expect` 太宽，比如“聊天设置”在任何聊天页都成立，直接续跑可能在错的会话里复制，还报成功。续跑、合并时挑版本、失败归因都要靠它，所以排在最前面（第 9 节）。

### 5.3 定时和自动触发

- **定时**：
  - 要准点的，用 `setExactAndAllowWhileIdle`。Android 14 起新装的 App 默认没有 `SCHEDULE_EXACT_ALARM`，安装引导里要带用户去“闹钟和提醒”打开。
  - 不要求准点的，用 WorkManager：一次性任务可以任意延迟，周期任务最短 15 分钟。
- **自动触发**，按成本从低到高：时间；充电或断电；连上某个 Wi-Fi；打开某个 App（无障碍本来就收到窗口事件，几乎零成本）；收到微信、QQ 的通知（**已定**）。
- **通知监听**：用户要在“通知使用权”里打开，侧载的 App 和开无障碍一样，要先“允许受限设置”。通知里有消息正文，只在内存里按包名和关键词匹配，日志只记“触发了几次”。
- **锁屏时**：在主屏上，无障碍要屏幕亮着、已解锁才能操作。有锁屏密码时，到点只能发一条通知：“到点了，解锁后点这里开始”。**虚拟屏不受这个限制**：Neo5 实测，带 `ALWAYS_UNLOCKED` 标志的虚拟屏在锁屏、熄屏时照常能启动 App、读树、截图、点击，手机始终保持锁定（第 6 节）。所以开了后台模式的用户，定时任务在锁屏时也能跑；没开的，退回发通知。
- 会改东西的步骤（发布、上传）由自动触发启动时，至少在刚开始的几个版本里，先在面板上请用户确认一次。

### 5.4 Android 14 的其他影响

- 用前台服务时，必须声明 `foregroundServiceType`。
- 精确闹钟、通知监听的授权，见 5.3。

## 6. 后台虚拟屏（已测，可行）

用户在主屏上做自己的事，任务在虚拟屏上跑。2026-10-29 在 Neo5（Android 14）上实测可行，13 项测试的结果和重跑步骤见 `docs/virtual-display-experiments.md`。

**实测结论**：
- **身份**：普通 App 不能把别的 App 启动到虚拟屏上（AOSP 的 activity 启动策略：Android 10 起，第三方 App 只能启动**自己的** Activity 到自己建的屏）。shell 身份可以：我们的建屏工具以 shell 身份运行，建屏、`am start --display` 都成功了。产品里用 Shizuku 提供同一个身份。
- **四个 App 都能跑**：微信、QQ、小红书、抖音在虚拟屏上显示正常。现有的无障碍服务能读树（QQ 290 个节点、抖音 701 个）、截图（124–208 ms）、做手势、点节点，不需要额外权限。微信照样靠截图加 OCR。
- **焦点**：只用 scrcpy 那组标志时，虚拟屏上的任何输入都会把顶层焦点屏切过去，用户在主屏打字时回车会失效。加上 `STEAL_TOP_FOCUS_DISABLED` 后，打字和回车都正常。
- **锁屏也能跑**：带 `ALWAYS_UNLOCKED` 的虚拟屏，在锁屏、熄屏时照常能启动 App、读树、截图、点击，主屏始终锁着（5.3）。
- **对前台几乎没有影响**：主屏滑动时掉帧率，没有虚拟屏是 0.09%；虚拟屏放抖音视频、同时跑 OCR 是 0.46%。
- **低分辨率能让检测快约 3.4 倍**（540x1200，像素少 4 倍），但准确率很可能会掉：这等于把检测最长边降到 1200，前台降到 1600 就已经掉了。准确率评测之前，虚拟屏先用和主屏相同的分辨率。

**要处理的问题**：
- **同一个 App 不能同时在两块屏上**（已实测）：用户在主屏打开任务正在用的 App，它的任务会被整个拉回主屏。运行时要盯住目标 App 在哪块屏，被拉走就暂停、发通知，等用户用完再“按状态继续”。
- **声音**：虚拟屏上 App 的声音从扬声器放出来（抖音实测）。可以考虑用 shell 身份临时静音（`appops set <包名> PLAY_AUDIO ignore`），未测。
- **授权链更长**：要装 Shizuku，用无线调试启动，手机重启后要重新启动一次。新用户最容易在这一步流失，所以后台模式做成可选的进阶功能，不开就照旧在主屏跑。
- **不能切加速输入法**：后台模式下用户可能在打字，不能切走他的键盘，只能用 0–5 号核（按 `docs/ocr-experiments.md` 4.9，检测慢约一倍，GPU 识别慢约 30%）。好在后台只有微信要 OCR（QQ、小红书、抖音走界面树，网站走接口），而且微信任务大多只做区域 OCR。
- **第一版已经跑通**（2026-10-29）：QQ、微信的任务包在虚拟屏上完整跑完，用户同时在主屏用别的 App。做法：
  - shell 服务（`app/.../shell/ShellServer`）由 `app_process` 从我们的 APK 启动，经 `ShellProvider` 把 binder 交给 App，只接受我们 App 的 uid，App 退出时它也退出；
  - 运行时在 `AgentService.display` 上读树、截图、点击，启动和返回通过 shell 服务；
  - 前台包名按屏判断（守住不变量第二条）；
  - 虚拟屏比主屏矮一个状态栏的高度，坐标统一换算成主屏坐标，任务包不用改。

  详见 `docs/virtual-display-experiments.md` 第 4 节。
- **还没做的**：
  - shell 服务现在要从电脑启动，App 重装或崩溃后要重启。要能跟着 App 启动：内置一个用无线调试启动 shell 服务的启动器（原理和 Shizuku 一样），或者接 Shizuku；
  - App 被用户拉回主屏后的暂停和“按状态继续”；
  - toast 会显示在主屏上（比如“已复制”），这是系统行为，改不了。
- **没测的**：长时间运行和风控（小号上连续跑几天）；`FLAG_SECURE` 页面（比如支付）截出来应该是黑的。

**性能**：安卓没有按屏幕分配 CPU / GPU 的接口，vivo 的核分组也是厂商写死的，我们只能管住自己：
- 虚拟屏用较低的帧率；分辨率要等 OCR 准确率评测后再定；
- 按 `PowerManager.getThermalHeadroom` 和前台 App 的类别（比如游戏）自动收缩 OCR：少开线程、在 CPU 和 GPU 之间选、降低频率，发热到一定程度就暂停；
- 一次只跑一个任务。

## 7. 以后再定：分发到微信

保留讨论记录，暂不决定。

- **三方一致：不让手机去点微信的“发送”**。它违反不变量“动作集不含发送”；网上对“自动发消息被封”的说法很多，但没有官方阈值，小号也可能被限制。
- **建议：分发不放在手机上做，交给网站后端**。用户上传的截图和数据本来就在网站上，后端可以：
  - 用**企业微信消息推送**（原群机器人）推到群里：webhook 接口，免费，支持文本、Markdown、图片、图文，文档里写有频率限制，常见的说法是每分钟 20 条；
  - 推给个人，用**服务号模板消息**，需要认证服务号。

  这是官方渠道，没有封号风险，管理员的手机也不用开着。还要实测：企业微信消息推送能不能发到有普通微信用户的外部群。
- **退路**：一定要发到某个个人号又不用企业微信时，任务包打开会话、选好图片，停在“发送”前，面板提示“确认发送”，由人来点。
- **隐私**：收集再转发用户截图属于处理个人信息，网站要在用户上传时告知并取得同意。

## 8. 其他建议（免费、省事）

- **分发零成本**：任务包和 App 更新放在静态文件托管（对象存储加 CDN，或 Gitee / GitHub Releases），靠签名保证安全，不用自己维护服务器。
- **一键体检**：运行前检查任务包签名、App 版本在不在 `testedWith` 里，以及无障碍、后台高耗电、通知、闹钟这些权限是否都开了。缺什么就直接跳到对应的设置页。
- **失败反馈只传结构**：用户可以主动导出一份只含结构和耗时的轨迹，发给管理员，每次都由用户点击决定。
- **管理员看板放在网站上**：用 `http` 步骤把成功、失败的次数和错误码报给管理员网站，不报内容。

## 9. 优先级

1. **每步唯一的 `screen` 识别，加上“按状态继续”**：续跑、合并、失败归因都靠它；后台模式里 App 被用户拉回主屏后，也靠它接着跑。
2. **后台模式**（第一版已跑通 QQ、微信，见第 6 节）：
   - shell 服务跟着 App 启动（内置无线调试启动器，或接 Shizuku）；
   - App 被拉回主屏时暂停，用户离开后“按状态继续”；
   - 小红书、抖音、夸克的任务包在虚拟屏上验证；
   - 低分辨率虚拟屏上的 OCR 准确率评测。
3. **任务包三层、节点 id 和来源、合并器**：先只在电脑上用测试跑通，不做界面。
4. **悬浮面板，加上认元素的补教和“重录这一步”**。
5. **受限的变量、表达式，加上 `when` / `forEach` 和加载时校验**。
6. **管理员证书和 `http` 动作**（过安全评审）。
7. **编辑器**（建立在 4、5、6 之上）。
8. **定时和自动触发**（含通知监听）。
9. **小实验**：系统分身在 Android 14 上能不能启动、无障碍能不能读到（大约半天）。

## 10. 不做

| 不做 | 为什么 |
|---|---|
| 手机自动点微信的“发送” | 违反不变量，有封号风险；改由网站后端推送（第 7 节） |
| 匿名或未签名的管理员发布 | 签名是唯一的信任根 |
| 正常路径上调用模型 | 慢，结果也不可预测；失败兜底另说（4.4） |
| 不经测试就自动套用的接口修改 | 猜错会静默地发布错误数据（第 2 节） |
| `while`、图灵完备的表达式 | 加载时没法校验（3.2） |
| 改包名重签名去克隆微信 | 微信校验签名，必然失败，还会触发风控；系统分身另测（第 9 节） |
| 给主屏和虚拟屏分配不同性能 | 安卓没有这个接口，只能自适应地收缩我们自己的消耗（第 6 节） |
| 同时跑多个任务 | 性能和焦点问题都会成倍增加 |
| 绕过锁屏 | 不应该做。虚拟屏在锁屏时运行不算绕过：主屏一直锁着，拿到手机的人也看不到、操作不了虚拟屏 |
